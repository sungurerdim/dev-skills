# GitHub features via `gh` (ds-issue)

All issue operations use the `gh` CLI. Never interpolate raw issue text into a shell string — pass bodies via `--body-file -` so newlines and shell metacharacters are inert.

**Zero local footprint.** This skill writes no files. Pass multi-line bodies to `gh` with a heredoc on stdin — no temp file, nothing to clean up:

```bash
gh issue create --repo <slug> --title "<title>" --body-file - <<'EOF'
<composed body>
EOF
# or, where --body-file - is unsupported, process substitution:
gh issue edit <n> --repo <slug> --body-file <(cat <<'EOF'
<body>
EOF
)
```

## Body is the record — comments are not

**The body is the single source of truth.** Decisions, scope changes, acceptance criteria, gate baselines, deferred items and closure evidence live in the body and are written there with `gh issue edit --body-file -`. Information put in a comment is information that gets skipped: comments are collapsed in the web UI, absent from a `--json body` read, and unordered against the body's own structure. Work has been left undone for exactly this reason.

**Rule:** new information → rewrite the body. Never post it as a comment.

```bash
# read the current body, edit it whole, write it back — the only update path
gh issue view <n> --repo <slug> --json body --jq .body
gh issue edit <n> --repo <slug> --body-file - <<'EOF'
<the full revised body, including its updated Log line>
EOF
```

**When a body edit is the wrong move** — the issue's premise no longer holds and the scope changed out from under it, so the remaining work is a different issue. Then:

1. Write a `## Closure` block into the original body: why it stops, what carries over, `Superseded by #K` (`#K` filled in after step 2 — a second edit).
2. Open the successor with `## Handoffs — Received from #N: <item>` in its body, and the original's context restated, not linked-to.
3. Link both ways: `gh issue edit <K> --repo <slug> --add-blocked-by <N>` where the order binds, and `gh issue close <N> --reason "not planned"`.

A closed issue whose closure reason exists only in a comment or only in the close event is not closed properly — the reason belongs in the body.

**The narrow cases where a comment is legitimate** — and none of them may carry a decision, a criterion, a gate, or a scope change:

| Legitimate comment | Why |
|--------------------|-----|
| Automated output posted by CI, a bot, or a linked PR | Machine-generated, append-only, not the skill's to relocate |
| A comment written by someone else | Not yours to rewrite — promote its requirements into the body instead (Phase 6 step 1) |
| GitHub's own cross-reference and close notices | Generated by the platform |

Anything this skill itself has to say goes in the body.

## Verified capability set (checked 2026-08-26, `gh` 2.97.0)

| Capability | Status | How it is used here |
|------------|--------|---------------------|
| Sub-issues (`--parent`, `--add-sub-issue`) | Available — native | Epic → sub-issue hierarchy (Phase 4) |
| Sub-issue limits | Available — 100 per parent, 8 nesting levels ([docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)) | Epic wider than 100 children → split the epic |
| Dependencies (`--add-blocked-by` / `--add-blocking`) | Available — GA 2025-08-21 | Binding order between sub-issues |
| Hierarchy in JSON (`parent`, `subIssues`, `subIssuesSummary`, `blockedBy`, `blocking`) | Available | `--status` / `--sweep` read these, never re-derive from body text |
| Issue types (`--type`) | Organization-only. `gh api /orgs/<org>/issue-types` → 404 on a user-owned repo (verified against `sungurerdim/uzengi`) | Probe first; on non-200 skip types entirely and use labels |
| Labels, milestones, assignees | Available | 1 type + 1 priority label; milestones only if the repo already uses them |
| Body update via `gh issue edit --body-file` | Available | The only way information is updated |
| Body maximum length | 65536 characters, from the API error string — **not stated on any official docs page**, so treat it as an observed bound, not a documented one | Over ~40k → the issue is an epic, split it |
| Body edit history | Available, GraphQL only (`userContentEdits`) — never surfaced by a normal read | Why the body carries its own `## Log` |
| Task lists (`- [ ] #123`) | Tasklist *blocks* are retired ([docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/about-tasklists)); a plain checkbox referencing an issue still renders and back-links, but is **not** a hierarchy | Portable fallback only, when native sub-issues are unavailable |
| Projects v2 field writes (`gh project item-edit`) | Available, but needs the `project` token scope (`gh auth refresh -s project`); the default `repo` scope is not enough | Out of scope for this skill — never assume the scope is present |
| Issue templates / issue forms (YAML) | Available (`--template`) | Not used: they shape human intake, and this skill composes the body itself |

Anything not in this table was not verified — do not build behavior on it.

**Version gate (once per run):** `gh --version` ≥ 2.94.0 → the native sub-issue / issue-type / dependency flags above exist (GitHub.com and GHES 3.17+; blocked-by/blocking need GHES 3.19+). Below 2.94.0 → REST/task-list fallbacks, and recommend upgrading.

**List calls truncate silently — always `--limit 1000`, then measure.** `gh issue list` and `gh search issues` return **30 items** when `--limit` is omitted. The 31st issue does not error, it just is not there: a 44-issue backlog reads as 30, dedup misses the duplicate, `--do --all` skips the tail, and `--status` reports a count that is simply wrong. Every list call passes `--limit 1000`, and the run **measures the returned count** (`… --json number --jq 'length'`) instead of eyeballing the list. Returned count == the limit → the set may still be truncated: raise the limit and re-read before quoting any number. A count that was never measured is never reported.

**Read-phase command allowlist:** `--status`, `--sweep` classification, and every `--preview` restrict `gh` to `issue view` / `issue list` / `search issues` / `label list` (+ `repo view` for the slug). Mutating commands (`issue create/edit/close`, `label create`) run only after the per-item confirmation the SKILL gates require (or, under `--auto`, the best-judgment resolution the SKILL gates specify).

## Dedup search (Phase 2) — run it, paste the output

The search is executed and its **real output** goes into the body's Dedup evidence block. A dedup verdict with no pasted command output is fabricated evidence.

```bash
# whole set, all states — open AND closed
# --limit is MANDATORY: without it gh returns 30 and drops the rest silently
gh issue list --repo <slug> --state all --limit 1000 --json number,title,state,labels,issueType,parent,subIssues,blockedBy,blocking
# gh < 2.94.0 fallback: --json number,title,state,labels
# measure what came back before quoting any count; == 1000 means possibly truncated → raise and re-read
gh issue list --repo <slug> --state all --limit 1000 --json number --jq 'length'
# keyword search across the repo — OMIT --state to search all states
# (gh search issues accepts only --state open|closed; omitting it searches both — verified)
gh search issues "<keywords>" --repo <slug> --limit 1000 --json number,title,state
# canonical single-issue read — the ONE detail read that --do, --status and --sweep all use
gh issue view <n> --repo <slug> --json number,title,body,labels,state,stateReason,comments,parent,subIssues,subIssuesSummary,blockedBy,blocking
```

`comments` stays in the canonical read for one reason only: to detect requirements someone else left there, so they can be promoted **into the body**. It is never where this skill puts information.

History / abandoned-decision docs (from the adapter's `historyDocs`) are read as files, not via `gh` — a superseded decision is not an issue.

## Create / refine (Phase 4)

```bash
gh issue create --repo <slug> --title "<title>" --body-file - \
  --label "<type>" --label "<priority>" <<'EOF'
<composed body>
EOF

gh issue edit <n> --repo <slug> --body-file - \
  --add-label "<type>" --add-label "<priority>" <<'EOF'
<composed body>
EOF
```

## Labels + issue types (Phase 4)

```bash
gh label list --repo <slug> --limit 100        # live taxonomy — never assume label names
gh label create "<name>" --color "<hex>" --description "<desc>"   # only if scaffolding is approved

# issue types: probe before use — 404 on user-owned repos and on orgs without types configured
gh api "/orgs/<org>/issue-types" --jq '[.[].name]' 2>/dev/null || echo "issue types unavailable — labels only"
```

Labels (1 type + 1 priority) are the portable default and stay the primary taxonomy. Native issue types complement labels where the probe succeeds — never replace them.

## Hierarchy: epic + sub-issues (Phase 4, oversized work)

```bash
# create the epic first, then each child linked natively on create
gh issue create --repo <slug> --title "<epic>" --body-file - <<'EOF'
<epic body>
EOF
gh issue create --repo <slug> --title "<child>" --parent <epic> --body-file - <<'EOF'
<sub-issue body>
EOF

gh issue edit <n> --repo <slug> --parent <epic>          # re-parent; --remove-parent to unlink
gh issue edit <epic> --repo <slug> --add-sub-issue <n>   # from the parent side
gh issue edit <B> --repo <slug> --add-blocked-by <A>     # binding order; --add-blocking is the inverse

# progress at the whole level, read not guessed
gh issue view <epic> --repo <slug> --json subIssuesSummary

# fallback (gh < 2.94.0) — REST sub-issue link:
gh api repos/<slug>/issues/<parent>/sub_issues -f sub_issue_id=<child-id>
# fallback (always renders, but is NOT a hierarchy) — checkboxes in the parent body:
#   - [ ] #childA
```

Split when the estimate exceeds the bounded-task threshold (≈5 files / one reviewable unit). Each child is a well-formed issue with its own Current/Target/Gates/Done. The epic body carries the whole's state and the binding order and nothing else — see [issue-template.md](issue-template.md) § Epic template.

## Milestones (optional)

Supported, never imposed. Repo already uses them → `gh issue edit <n> --milestone "<name>"`. None exist → skip silently; do not create a milestone scheme the repo did not ask for.

## Closing with evidence (Phase 6, `--do`)

Evidence goes **into the body**, then the issue closes.

```bash
# 1. write the Closure block + the tick marks + the Log line into the body
gh issue edit <N> --repo <slug> --body-file - <<'EOF'
<full body: Done items ticked with their observed output, ## Closure block, ## Log line>
EOF
# 2. close
gh issue close <N> --repo <slug> --reason completed        # done + verified
gh issue close <N> --repo <slug> --reason "not planned"    # obsolete / superseded / stale
```

`completed` only when the aggregate gate is green and (for fixes) a red-proven regression test exists. `not planned` for the stale/superseded issues found in re-verify — with the closure reason written into the body first.

Where the work goes through a PR, `Closes #N` in the PR or commit body auto-closes on merge — the body still gets its Closure block before the merge, because the auto-close writes nothing.

## Commit message

```
<type>(<scope>): <summary>

<what changed + why>
Closes #<N>
```
