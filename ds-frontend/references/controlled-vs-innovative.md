# Controlled vs. Innovative Mode

> Two distinct workflows for `/ds-frontend`. Picking the wrong one is the most common cause of "the AI gave me generic UI" frustration.
>
> **Controlled** = code that ships to production. Tokens, accessibility, responsive — all enforced. No improvisation.
> **Innovative** = exploration. Tokens may be inferred, accessibility softened, novel patterns allowed. Output is for design review, not direct ship.

This file is loaded by `/ds-frontend` when `--style-mode=<controlled|innovative>` is set.

---

## Controlled Mode (default)

**Use when:** writing or auditing code that will be deployed.

**Enforced contracts:**

| Domain | Rule |
|--------|------|
| Tokens | Every color/spacing/radius/shadow value MUST resolve to a design token. Hardcoded literal → CRITICAL finding. |
| Accessibility | WCAG 2.2 AA enforced strictly. Contrast <4.5:1 → CRITICAL. Missing focus-visible → CRITICAL. Interactive without accessible name → CRITICAL. |
| Components | Match project's existing component library. New components require justification ("this pattern doesn't exist yet"). |
| States | Every interactive component MUST have empty / loading / error / success / disabled / focus-visible states. Missing → HIGH. |
| Responsive | Container queries or breakpoints required. Fixed-width >breakpoint without override → HIGH. |
| Theming | Dark mode parity required if light mode exists. Missing dark mode → HIGH. |
| Motion | `prefers-reduced-motion` respected. Autoplay disabled by default. Duration >500ms requires justification. |
| Aesthetic adherence | If `--aesthetic=<preset>` set, preset's `forbidden` list is enforced as audit rules. |

**Output:** production-ready code. Audit mode reports CRITICAL/HIGH/MEDIUM/LOW with file:line refs.

**When skill encounters ambiguity:** ask the user. Never invent a pattern.

---

## Innovative Mode

**Use when:** exploring design directions, building a prototype, generating reference UIs, doing design review with stakeholders.

**Relaxed contracts (vs Controlled):**

| Domain | Relaxation |
|--------|-----------|
| Tokens | Hardcoded values allowed if marked `<!-- innovative -->` or in a file matching `**/explore/**`, `**/proto/**`, `**/sandbox/**` |
| Accessibility | WCAG AA still encouraged but not blocking. Contrast warnings → MEDIUM (not CRITICAL). |
| Components | Novel patterns allowed without library precedent. AI may invent component names with `Proto` prefix (`ProtoCard`, `ProtoNav`). |
| States | Only "default" + "loading" required for prototypes. Other states optional. |
| Responsive | Single-viewport prototype OK. Marked as "desktop-only prototype" or similar. |
| Theming | Single theme acceptable. |
| Motion | Bold motion patterns encouraged for exploration. Document them. |
| Aesthetic adherence | If `--aesthetic=<preset>` set, preset is treated as starting point — deviations allowed and encouraged if they sharpen the mood. |

**Output:** prototype code, marked clearly. Files containing prototypes get a header comment:

```
/* eslint-disable @design/strict-tokens */
// PROTOTYPE — generated by /ds-frontend --style-mode=innovative
// Not for production. Ship-readiness gate: re-run with --style-mode=controlled.
```

**When skill encounters ambiguity:** propose 2-3 directions and ask which to pursue. Never silently pick.

## Mode Selection Matrix

| Scenario | Mode |
|----------|------|
| `/ds-frontend` on existing repo, no `--style-mode` flag | controlled |
| `/ds-frontend` on a `proto/` or `explore/` directory | innovative |
| `/ds-frontend --mode=design` (token / catalog generation) | controlled (tokens are ship contracts) |
| User says "explore", "experiment", "try", "concept", "what if" | innovative |
| User says "audit", "review", "ship", "production", "release" | controlled |
| User says "moodboard", "direction", "alternatives" | innovative |

When unclear: ask.

---

## Translating Innovative → Controlled

When a prototype is approved and needs to ship:

```bash
/ds-frontend --mode=audit+fix --style-mode=controlled --scope=tokens,a11y,states --target=src/proto/checkout-v2/
```

Skill will:
1. Replace hardcoded values with tokens (or flag if no token matches and prompt user to add).
2. Add missing accessibility attributes.
3. Add missing component states.
4. Move file out of `proto/` / `explore/` to its production location (user-confirmed).
5. Strip the prototype header comment.

## Prompt Anchors per Mode

These are the prompts the skill embeds when invoking sub-agents or generating code.

### Controlled prompt anchor

> "Generate UI code that ships to production. Use only design tokens — never hardcoded values. Pass WCAG 2.2 AA. Cover all interactive states. Match the project's existing component library style. If a needed pattern doesn't exist, propose adding it but stop before implementing."

### Innovative prompt anchor

> "Explore a design direction. Tokens may be inferred. Novel patterns are encouraged. Optimize for the named aesthetic mood, not for ship-readiness. Mark output clearly as prototype. Include a one-paragraph rationale per major decision so the designer can evaluate."

---

## Anti-Pattern: "Mode Drift"

Mode drift = starting in one mode and silently producing the other's output. The two most common drifts:

1. **Innovative drifting into Controlled:** AI invents tokens for hardcoded values rather than flagging them. Controlled requires the user to author the token. → Fix: in Controlled mode, the skill never invents new token names — it asks.
2. **Controlled drifting into Innovative:** AI relaxes accessibility because the codebase has historical violations. Controlled never relaxes WCAG AA. → Fix: distinguish "existing finding" (don't auto-fix without approval) from "new code" (must comply).
